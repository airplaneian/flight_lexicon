Contrail

An AT Protocol lexicon for flight records — and a tool that writes some, so you can see what it looks like in use.

What the record says

A flight record asserts that a particular flight existed. That is all. It is not a log entry about you, and it does not claim you were aboard.

Your connection to the flight — passenger, pilot, student, observer — rides along as an optional relationship field. Leave it off and the record makes no claim either way, which is exactly what you want when the record came from ADS-B data about somebody else's aircraft.

This split follows the pattern Smoke Signal uses for events and RSVPs: the event record says a thing exists, and attendance is a separate claim. Here the claim is a field rather than a second record, but the framing is the same.

Only one field is required

createdAt, and nothing else. This is the most important property of the schema and everything else follows from it.

Absent means unknown or not applicable. Never zero, never an empty string, never a placeholder. A flight where you know only the date and the tail number is a valid record. So is one with all thirty fields filled.

A tool that wants complete data should reject incomplete input itself. The schema cannot do that job, and pretending otherwise would make it useless for general aviation, where most of the commercial fields are meaningless.

The one exception: absent relationship means no claim is being made, not that the relationship is unknown.

Two flights, both valid

A widebody on a transpacific sector and a Super Cub flying circuits at a grass strip are the same kind of record. The second one has no flight number, no airline, and no airport code — and it is still complete.

Origin and destination are the same place. Local flights are ordinary and the schema treats them as such.

Everyone writes their own copy

Because the record is about the flight rather than about the author, several people on the same aeroplane will each write a record describing it. None of them is canonical. That duplication is expected and by design — there is no authority that could issue a global flight identifier, so the schema does not pretend one exists.

It does mean readers need to recognise two repositories describing one flight, so the identity fields carry more weight than they would in a personal-log model. Write them consistently:

Commercial date + operatingAirline + flightNumber
General aviation icao24 + actualTakeoff

operatingAirline is the ICAO designator — UAL, not UA. IATA airline codes get recycled between carriers, which makes a historical record tagged with one ambiguous. registration is uppercase with no hyphens, so G-VBOW and GVBOW do not become two aircraft.

What the schema leaves out

Duration, distance, great-circle miles. All derivable from the times and places already in the record. Storing them guarantees that records written by different tools disagree with each other.

Airport names, coordinates, elevations. Reference data about the world, not an assertion by the author. It does not belong in anybody's repository. The only exception is place.geo, for landing sites that no identifier system covers.

A global flight ID. No authority exists to issue one.

Times carry offsets

Eight timestamps, the standard out/off/on/in set, each scheduled and actual. All optional — a general aviation record will usually have a takeoff and a landing and nothing else.

Every one is written with an explicit UTC offset and no fractional seconds. The Lexicon specification flags two round-tripping ambiguities for datetimes — lost precision, and trailing fractional-second zeroes — and a fixed convention avoids both.

Try it

This imports a Flighty CSV export into your own repository as flight records. It runs entirely in this page: your file is parsed in the browser and never uploaded anywhere. There is no server to upload it to.

Before you write anything

A complete flight history is a movement history. Once these records are in your repository they are public and permanent, and anyone can read from them where you are based, how often you travel, and when you are away from home.

This is true regardless of what the records claim. The relationship field being optional does not change it — records about flights sitting in your repository disclose your connection to those flights either way.

The schemas

Published to did:plc:5jsivedaksbcc4n2epiegflk and resolvable by NSID.

  • com.airplaneian.contrail.temp.flight — the record
  • com.airplaneian.contrail.temp.trip — groups flights into a journey
  • com.airplaneian.contrail.temp.defs — the shared place definition

These are under a temp namespace while the shape settles. Published lexicon constraints can never be loosened, so the stable names are not claimed until real data has been through them.

Contrail is a demonstration. The lexicon is the point; this tool exists to prove the schema works and to give people a reason to write records with it.
